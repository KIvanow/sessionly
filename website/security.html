Security

Last updated 16 November 2026

In short

  • Full prompts, file contents and command output stay on the developer's machine, in files only that user can read. Nothing leaves the machine until it is connected to a server.
  • The default upload contains no text from prompts, commands or files, and no absolute paths. Previews and line hashes are separate switches, off by default, and sessionly export prints exactly what would be sent.
  • The capture hook only observes. It cannot block or change an agent's session, and it never opens the sign-in files of Cursor or Grok.
  • Access to a server is by token. Tokens are stored as SHA-256 hashes; a member reads only their own sessions, and the token the GitHub Action uses can report pull requests and nothing else.
  • Sessions of cloud agents are captured by a script committed to your repository. In a sandbox it fetches one fixed version of the program and runs it only if its checksum matches. Where those sessions are sent is set in the cloud environment, never in the repository.
  • The program and the server phone nothing home: no telemetry, no update checks, and licenses are verified offline. The dashboard counts which of its pages are opened, and nothing of what they show or of where it runs; a self-hosted server can turn that off.
  • Found a problem? Email kristiyan@sessionly.dev. The code is public at github.com/KIvanow/sessionly.

Sessionly is operated by Kristiyan Ivanov, an individual. This page describes what the software does to protect the sessions it records, as it is built today. It is written from the code, which you can read yourself; where this page and the code disagree, the code is right and I would like to hear about it. It is not a certification: Sessionly has no SOC 2 or ISO 27001 audit.

Sessionly can be self-hosted, where hosting, TLS and backups of a server are yours to arrange, or used as the hosted service at app.sessionly.dev, which is open and free during early access. How that is hosted and backed up is under The hosted service below.

On the developer's machine

What is kept, and who can read it

The sessionly program keeps everything under ~/.sessionly:

  • The raw capture: every hook event as the agent sent it, including full prompts, file contents and command output. Files are created with mode 0600 and directories with 0700, so only your user can read them. The raw capture is never uploaded.
  • The ledger: one record per session in a local SQLite file, also 0600. A record holds metadata and short previews, not content: for a prompt, its length, SHA-256 and first 200 characters; for a tool call, its tool, status, duration, file path, a hash of its input, the size of its output and a one-line summary.
  • The configuration, including the server's address and your token, in a file readable only by you. The token is never printed.

There is no retention limit yet: the raw capture grows until you delete it. Deleting ~/.sessionly removes everything Sessionly has kept on that machine.

The capture hook

  • It only observes. sessionly install registers 20 events that report what happened. Events that change the agent's behaviour when hooked (creating and removing worktrees, switching models) are left out on purpose.
  • It cannot get in the way. The hook appends one line under a file lock, never prints, and always exits 0, whatever its input or arguments, so a capture failure cannot block or alter a session. If another capture holds the file for more than 1.5 seconds, it writes anyway instead of waiting.
  • It is careful with your settings. Install adds, and uninstall removes, only hook entries whose command is exactly Sessionly's own. Other hooks and settings, file permissions and a symlinked location are kept; the file as it was before the first change is saved beside it and never overwritten; a settings file that is not valid JSON is left untouched.

Other agents' files

Sessions from Cursor and Grok are read from the transcript and session files those agents keep. Their sign-in files are never opened.

What leaves the machine

Nothing, until you run sessionly connect. The program makes one kind of network connection on its own: the upload to the server you connected. It sends no telemetry and does not check for updates. The one other command that reaches the network is sessionly install --repo, which reads a release's checksums from GitHub unless you give it a file. Once connected, before a record is uploaded:

  • Paths are made relative: to the repository for files inside it, otherwise to the home directory (~/…). No absolute path under your home directory is sent.
  • The content level is applied. The default, metadata, sends counts, sizes, timings, tool names, statuses, relative file paths, models, tokens, cost, rewrite figures and the git user and remote. It sends no text from prompts, commands, search patterns, URLs, errors or titles, and no content hashes. previews, which you switch on yourself, adds the 200-character previews and the hashes.
  • Line hashes are a separate switch, off by default. When on, the upload includes, per changed file and model, the first 8 bytes of the SHA-256 of each line the agent added, without the whitespace at its ends. Blank lines and lines with no letter or digit are left out.

sessionly export <session> prints the exact payload for any session, connected or not, and sessionly schema upload prints its JSON Schema.

In transit

The program refuses plain http:// for any server that is not on the same machine, so an upload to a remote server always goes over HTTPS. The token travels in the Authorization header.

In a cloud agent's sandbox

A Claude Code session on the web or a Cursor cloud agent runs in a sandbox the platform starts, where nothing from a developer's machine exists. Capture there is set up by sessionly install --repo, which writes a script, .sessionly/hook.sh, and hook entries that run it, for you to commit.

  • The script does nothing on a person's own machine. In a sandbox it downloads the program, of the one version named in the script, from the project's GitHub releases, once per sandbox, and runs it only if the download's SHA-256 is the one written into the script. It prints nothing and always exits 0. As with any hook a repository carries, whoever can change the script can change what runs in the sandbox: review changes to it as you would code.
  • Where sessions are sent is not in the repository. The server's address and a token are given to the cloud environment as secrets. The program reads them from the environment and does not write them to disk. Without them the session stays in the sandbox and goes when it does.
  • Who started the session is asked of the platform, since git in a sandbox is set up as the agent: Claude Code names the person in the sandbox's environment, Cursor through a socket it serves inside the sandbox. From it the program reads the agent's id, what started it and the person's email address, and nothing else.
  • What a shell command changed is found by comparing the working tree before and after the command, with git and an index and object store of the program's own under ~/.sessionly. The repository's own index, objects and HEAD are not written. The changed lines are kept in the sandbox's capture like any other edit, and an upload carries of them what it carries of any edit: counts, and hashes only if line hashes are switched on.

On the server

  • Tokens (sly_…, 24 random bytes) are shown once when created. The server stores their SHA-256 hash and looks them up by it. A token can be revoked at any time, and when it was last used is recorded. There are no passwords.
  • Roles. A member token uploads sessions and reads only the sessions filed under its owner. An admin token reads everyone's and manages tokens. A ci token, for the GitHub Action, can report pull requests and check that it is accepted; every other request is refused. An env token, for a cloud environment, can upload sessions and check that it is accepted; every other request is refused.
  • Ownership. An upload is filed under the owner of the token that sent it, whatever name the record carries, and a session uploaded by one person cannot be replaced by another. The one exception is an env token: a cloud session it uploads is filed under the person the platform named. Whoever holds such a token can therefore upload a session in anyone's name, so it belongs in a cloud environment's secrets and nowhere else.
  • Validation. Every upload is checked against the published schema and refused if it does not match; a record marked as local-only is refused; a body over 32 MB is refused.
  • The first admin token comes from the server's environment, for use before any token exists. It is compared in constant time and never stored.
  • Logs. The server does not write a log of requests. Unexpected errors are written to its standard error.
  • The dashboard keeps the token in the browser's local storage and sends it as a header. It loads nothing from other sites. Its only cookies belong to signing in with Google or GitHub: one from leaving for the provider until coming back, so that only the browser that left is taken back, and one from coming back until an org is chosen, which is what carries the sign-in. Both last ten minutes at most, cannot be read by scripts (HttpOnly), are sent only on same-site requests (SameSite=Lax), and are removed when the sign-in ends. Served over HTTPS, as the hosted service always is, they are also limited to the dashboard's own host and to HTTPS (the __Host- prefix and Secure). Nothing is tracked with them, and signing in with a token sets none. It counts which of its pages are opened by sending a count to PostHog's EU cloud (https://eu.i.posthog.com). The count is written out in the dashboard's own code, with no analytics library: the page's name, whether the server is hosted or self-hosted, and an id made up for that one load of the page. Nothing is read from the browser to put in it. It is sent as a GET request made with no referrer and no credentials, so the browser adds no Origin header, no Referer and no cookie: nothing in the request names the address the dashboard runs at, which for a self-hosted server is a name inside someone's network. (A POST would not do: Chromium sends the page's origin with every cross-site POST.) PostHog's servers see the IP address the request comes from and the browser's standard headers, as any server does. The dashboard's Content Security Policy allows that one address only while counting is on. Organisations, people and what pages show are never sent, nothing is stored in the browser for it, and a browser that sends Do Not Track or Global Privacy Control is not counted.

Self-hosting defaults

Started directly, the server listens on 127.0.0.1 only. The Docker Compose file publishes the server's port and keeps Postgres inside the Compose network, with a fixed database password that is not reachable from outside it. Put the server behind HTTPS before anyone outside the machine uses it; the program will not upload to it otherwise. SESSIONLY_TELEMETRY=off (or DO_NOT_TRACK=1) stops the dashboard counting its pages, and its policy then allows no address but its own.

The hosted service

The hosted service runs the published code, built from the public repository, and everything above about the server holds for it. What is particular to it:

  • Where it runs. One virtual machine at DigitalOcean in Frankfurt, Germany, with its data in a DigitalOcean managed PostgreSQL database in the same region. Nothing of it is stored anywhere else.
  • Orgs are kept apart twice. Every query names the org of the token that asked. Underneath, each request runs in the database as a role that cannot log in and that row-level security confines to that one org: a query that forgot to name its org would get nothing of anyone else's, and a write into another org is refused by the database itself.
  • Signing in. People sign in with Google or GitHub; there are no passwords. Only which account it is and its verified email addresses are asked of the provider. The account that first signs in to an org under an address is from then on the only one that gets in as that person there, whoever else comes to hold the address. Nobody is taken into an org they were added to without being shown which one it is and who added them.
  • In transit. HTTPS only, with a certificate from Let's Encrypt; plain HTTP is redirected, and Strict-Transport-Security is sent. The server connects to its database over the provider's private network, with TLS, and checks the database's certificate against the provider's certificate authority.
  • What is reachable. From the internet, the machine answers on ports 80 and 443 only. The database accepts connections from that machine alone. The machine is administered over SSH with a key, from named addresses; passwords are not accepted.
  • At rest and backups. The database is encrypted at rest by DigitalOcean, which backs it up daily and keeps what is needed to restore it to any moment of the last seven days. There are no other copies.
  • Limits. Requests, sign-ins, new orgs and wrong invitation codes are counted and limited, by network address, by token and by account.
  • What it is not. It is one machine and one database node in one region: if either is down, the service is down until it is back. One person runs it. There is no SOC 2 or ISO 27001 audit.

Pull requests

The GitHub Action and the program both send hashes of lines, never the lines. The server compares them to tell which lines of a pull request an agent added. No source code leaves GitHub or anyone's machine for this.

  • The Action is plain JavaScript with no dependencies. It needs pull-requests: read and nothing else unless you ask it to comment.
  • It authenticates with a ci token kept as a repository secret. If that token leaks, it can submit pull request reports; it cannot read sessions, reports or tokens.
  • GitHub does not give secrets to workflows run from forks, so pull requests from forks are not reported.
  • The commit email addresses the Action sends are used to pick the sessions to compare with and are not stored.

Licenses

A Business or Enterprise license is a JSON file with an Ed25519 signature over its contents. The server verifies it against a public key built into the code, when it is installed and each time it is loaded, and accepts it only if it names the install's own org. Nothing is sent anywhere to check it. The private key is not in the repository.

This website

The website is static HTML, one stylesheet, two typefaces and one script, all served from the site itself. The script is Vercel Web Analytics, which counts page visits without cookies and without keeping IP addresses. The website sets no cookies. It is served with a Content Security Policy of default-src 'none' that allows only its own script, stylesheet, fonts and images, and connections back to itself, and sends X-Content-Type-Options, X-Frame-Options and Referrer-Policy headers. It is hosted by Vercel, which keeps request logs.

What Sessionly cannot protect you from

  • A preview can contain a secret. The first 200 characters of a prompt or a shell command are whatever was typed. They are kept in the local ledger, and uploaded if previews are on. Sessionly does not scan for secrets.
  • Paths and hashes still say something. A relative path names files in your repository. A line hash is 64 bits of a SHA-256: it does not give the line back, but a short or common line can be guessed and checked against it. Treat line hashes as you would the names of your files.
  • A token is the whole key. Anyone holding an admin token can read every session in the org. Tokens do not expire on their own; revoke them when people leave.
  • Identity is a label. The name and email in a record come from git configuration, or for a cloud session from the platform, and are not verified. The server trusts the token, not the name.
  • Anyone with your user account can read the capture. File permissions keep other users out, not other programs running as you, and the files are not encrypted.

Reporting a vulnerability

If you believe you have found a security problem in Sessionly or this website, please email kristiyan@sessionly.dev with enough detail to reproduce it. I read that address myself. Please give me a reasonable window to fix the issue before you publish it, and do not access, change or delete other people's data while demonstrating it. There is no bug bounty.

The whole codebase, including the capture program, the server, the dashboard and the GitHub Action, is public at github.com/KIvanow/sessionly, with everything outside ee/ under Apache-2.0. Run it yourself and read what it does.
