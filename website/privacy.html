Privacy Policy

Effective as of 16 November 2026

In short

  • Sessionly is run by me, Kristiyan Ivanov, an individual, not a company.
  • The sessionly program keeps what it captures on your own machine. It sends nothing to me. It uploads only to a server you connect it to, and by default only metadata: no text from prompts, commands or files.
  • A self-hosted Sessionly server sends nothing to me either. Its dashboard counts which of its pages are opened, and nothing of what they show or of where it runs, unless whoever runs it turns that off.
  • The hosted service is not open yet. This policy already says what it will store, because it runs the same published code; where it runs and which providers it uses will be added here before it opens.
  • This website sets no cookies. It counts visits with Vercel Web Analytics, which uses no cookies and keeps no IP addresses. It is served by Vercel, which keeps request logs.
  • I do not sell personal information.

Sessionly (“Sessionly,” “I,” “me,” or “we”) is a ledger of AI coding agent sessions: what was asked, which tools ran, which files changed and what it cost. It is operated by Kristiyan Ivanov, an individual (“the operator”). This Privacy Policy describes how I process personal information collected through the website at sessionly.dev, the hosted Sessionly service when I offer it (the “Hosted Service”), the sale of licenses, and emails you and I exchange (collectively, the “Service”).

The Service is intended for businesses and developers. When an organization (“org”) uses Sessionly for its team, that org decides whose sessions are collected, what an upload contains and who may see it. If you are an engineer whose sessions your employer or client collects with Sessionly, they are responsible for that collection; please direct questions about it to them first.

The software on your machine, and self-hosted installs. The sessionly program stores what it captures in a folder on your own machine (~/.sessionly). It does not report usage, telemetry or account data to me and does not check for updates. Its only network connection is the upload to the server you connect it to with sessionly connect; until you do that, nothing leaves the machine. If you run the Sessionly server yourself, everything described below is stored on your infrastructure, not mine, and license files are verified offline. The one exception is the dashboard's page counts, described under “Automatic data collection”, which you can turn off with SESSIONLY_TELEMETRY=off. This policy therefore applies to local and self-hosted use only to the extent you contact me, buy a license, or use the website.

Personal Information I Collect

Information you provide

  • Communications data from our exchanges, such as when you email me for support, to ask about a license or to be told when the Hosted Service opens: your email address, your name if you give it, and what you write.
  • License data. If you buy a Business or Enterprise license: the name and identifier of your org, the edition, the number of people it covers, its dates, a contact email address, and the billing details needed to issue an invoice. The license file itself contains the org identifier, edition, features, seats and dates, and no personal information.
  • Account data on the Hosted Service: for each access token, the email address it is issued to (stored lower-case), an optional name, its role (admin, member or ci), and when it was created, last used and revoked. Only a hash of the token is stored. There are no passwords.

Information uploaded to the Hosted Service

A machine connected to the Hosted Service uploads one session record for each coding agent session. With the default content level (metadata) a record contains:

  • a random identifier of the machine, which agent ran the session (Claude Code, Cursor or Grok), the session's identifier, and when it started and ended;
  • the git user name and email address and the repository's remote address, as set in git on that machine, or, for a session that ran in the cloud, the email address the platform gives for the person who started it. They are a label, not a verified identity;
  • counts and timings: prompts and how long each turn took, tool calls with the tool's name, status, duration and the size of its output, subagents, permission requests;
  • the files the agent read or changed, as paths relative to the repository or to the home directory, with lines added and removed;
  • models, token counts and cost;
  • the rewrite measurement: how many of the lines the agent added are still in each file.

Two things are added only if the person uploading switches them on:

  • Previews (sessionly settings --content previews): the first 200 characters of each prompt, a one-line summary of each tool call (the shell command, search pattern or URL, cut to 200 characters), the first 200 characters of an error, the session's title, and SHA-256 hashes of prompts and tool inputs. A preview can contain anything that was typed or run, including personal information or a secret.
  • Line hashes (sessionly settings --line-hashes on): for each changed file and model, a short one-way hash of every line the agent added. A hash does not give the line back, but a short or common line can be guessed and checked against it.

If an org adds the Sessionly GitHub Action to a repository, the Action sends a pull request report when a pull request is opened, pushed to, reviewed and closed: the repository's name, the pull request's number, title and address, its author's GitHub user name, its state, branch names and dates, counts of commits, reviews, review comments and review rounds, and, per changed file, hashes of the lines the pull request adds. The email addresses on the pull request's commits are sent with each report so that lines are matched only to sessions by the people who committed; they are used for that comparison and are not stored.

What is never uploaded: full prompts, the agent's replies, file contents, the output of commands, the raw capture kept on the machine, and absolute paths under a home directory. No source code is uploaded, by the program or by the Action.

Automatic data collection

  • This website (sessionly.dev) is static and sets no cookies. It loads one script, Vercel Web Analytics, from the site itself. It counts which pages are visited, from which referring site, country, browser and device type, without cookies; visitors are not followed from one day to the next, and no IP address is kept. Vercel, which serves the website, keeps its own request logs (including IP addresses) under Vercel's Privacy Policy.
  • The dashboard keeps your access token in your browser's local storage so you stay signed in. Its only cookies are two short-lived ones that are part of signing in with Google or GitHub, described under “Cookies and tracking” below. It counts which of its pages are opened with PostHog, in PostHog's EU cloud. Each count is three things: the page's name (such as “sessions” or “team”), whether the server is hosted or self-hosted, and an id made up for that one load of the dashboard, which is gone when the page is closed or reloaded. Nothing is read from your browser to put in it, and it never includes the address the dashboard runs at, an org, a person, a session or anything a page shows. The dashboard sends it with a few lines of its own code, as a request to which the browser adds no cookie and neither of the two headers (Origin and Referer) that would say which site it comes from. Like any server, PostHog's sees the connection a count arrives on: its IP address, and what a browser says of itself with every request (its kind, its system and its languages). Each count asks PostHog not to look the address up for a location, and the PostHog project is set to discard IP addresses. Nothing is stored in your browser for it, and a browser that sends Do Not Track or Global Privacy Control is not counted. Whoever runs a self-hosted server can turn the counting off.
  • Server logs. The Sessionly server does not write a log of requests. The infrastructure in front of the Hosted Service will keep ordinary connection logs (IP address, time, address requested, status); how long they are kept will be stated here before the Hosted Service opens.
  • Email. I do not embed tracking pixels, and I do not use open or click tracking.

Data Retention

  • Uploaded sessions and pull request reports are kept while the org's account on the Hosted Service exists, and deleted when the org asks me to delete them or closes its account. Uploading a session again replaces the earlier copy.
  • Tokens are kept while the account exists. A revoked token stops working at once; its entry (email, role, dates, never the token) is kept so the org can see who had access.
  • License and invoice records are kept as long as tax and accounting law requires.
  • Emails are kept as long as they are needed to answer you and to keep a record of what was agreed.

When I no longer need personal information, I delete or anonymize it. To delete your account and its data, email me (see below). What the sessionly program keeps on your own machine is yours to delete: remove ~/.sessionly.

Security

Only a hash of each access token is stored. The program refuses to upload over plain HTTP to anything but a server on the same machine. A member's token reads only that person's sessions, and a token for the GitHub Action can report pull requests and nothing else. The security page describes these measures and their limits. Still, security risk is inherent in all internet and information technologies, and I cannot guarantee the security of your personal information.

Cookies and tracking. This website sets no cookies. The dashboard sets cookies for one thing only: signing in with Google or GitHub. When you leave for Google or GitHub, one cookie lets the dashboard recognise the same browser when it comes back; a second one carries the sign-in from that moment until you have chosen which org to sign in to. Each holds a random value that means nothing outside that one sign-in, lasts ten minutes at most, is removed when the sign-in is finished or cancelled, is sent only to the dashboard itself, and cannot be read by scripts. If you sign in with a token, no cookie is set at all. These cookies are not used to track you, to measure anything or to advertise, and nothing about you is sold or shared for advertising. The dashboard uses your browser's local storage only to keep you signed in; signing out or clearing it removes the token. The website counts visits with Vercel Web Analytics, and the dashboard counts which of its pages are opened, as described above; neither stores anything in your browser. There is no advertising and there are no cross-site trackers. Because the only cookies are ones that signing in cannot work without, there is no cookie banner.
