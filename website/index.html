A ledger for AI coding agents

What your agents did. What it cost. What survived.

Sessionly records every Claude Code, Codex, Cursor and Grok session: what was asked, which tools ran, which files changed and what it cost. Then it counts how many of the agent's lines are still in the file later, and still in the pull request after review.

Neutral by design

Lab-neutral, and private by default.

Sessionly is not any agent maker's tool. It reads every agent's sessions the same way and says where one records less, so a comparison is not scored by one of the players.

Every agent, one way

Claude Code, Codex, Cursor and Grok, on a machine or in the cloud, mapped to the same tool names and the same session record.

A ledger, not marks in your repo

Nothing is written into your commits: no notes, no trailers. Pull requests are matched to sessions by hashes of the lines, on your server.

Uploads are opt-in

Nothing leaves a machine until you connect a server. The default upload has no text from prompts, commands or files, and source code is never sent.

How it works

A small local program does the work. A server is optional.

The sessionly binary sits beside your agents and keeps a ledger in ~/.sessionly. If your team runs a Sessionly server, the same records are uploaded there and shown in a dashboard. What an upload may contain is on the security page.

  1. Capture

    A hook appends each agent event to a local file in 2–4 ms. It only observes: it cannot block or change a session.

  2. Read

    Tokens, models and cost come from the transcripts and session files the agents keep themselves.

  3. Normalize

    Both become one record per session in a local SQLite ledger: prompts, tool calls, files, subagents, cost.

  4. Measure

    On every sync, the lines each session added are counted again in the files as they are now.

  5. Upload

    Only if you connect a server. Paths are made relative and the content level you chose is applied first.

What you get

The session, the cost, and what became of the code.

Cost you can trace

Tokens and cost per session, model and subagent, summed per person, repository, model, agent or day. The agent's own recorded figure is used where there is one; an estimate is marked as an estimate.

Rewrite rate

For every file a session changed, Sessionly keeps hashes of the lines the agent added and counts how many are still there later. Moved or re-indented code counts as kept.

Search from the terminal

sessionly list, summary and show filter by repository, person, model, agent, file, date and cost, and search prompts and commands. Every command takes --json.

Team dashboard

Cost per day; totals by agent, person, repository and model; the files agents changed in each repository; and every session down to its prompts, tools and subagents.

Past sessions

sessionly import rebuilds sessions from the files the agents still keep, so the ledger does not start empty. On one machine, 100 sessions in 2.5 GB of transcripts took about a minute.

You choose what is uploaded

The default upload has counts, timings and relative paths but no text at all. Previews are opt-in, and sessionly export shows the exact payload before anything is sent.

Tokens and roles

Each token belongs to one person. A member sees their own sessions, an admin sees the team, a ci token can only report pull requests, and an env token, for a cloud environment, can only upload. Only a hash of each token is stored.

What a pull request cost

What was spent getting a pull request merged: the cost of every session that gave it lines, review rounds included, and still counted when review takes those lines out. A session that worked on several is split between them. Beside it, the cost of an agent line that got through review. Marked "at least" where it is a floor and ~ where it is an estimate.

Review runs

Each time a review command ran in a session: /code-review, /review, /security-review, /ultrareview and Codex's /review. When, with what effort, for which pull request, what its subagents cost, and how many findings it reported where the agent says.

Review bots

Who reviewed a pull request, people and each review bot apart, with what each commented, and how many rounds of review followed only a bot's feedback, only people's, or both. A Review bots table sums it per bot.

Figure history

Under a pull request's figures, each time they moved: when, what prompted the report and why, from new commits to a session uploaded since or a newer Action.

Match again

A session uploaded after the merge? Match again matches the pull request against the sessions the server holds now, without asking GitHub. The page says when a repository reports with an older Action, and sessionly status when a newer CLI is out.

Your data, out or gone

On the hosted service the owner can download the whole organisation as JSON lines, or delete it from the Team page. Removing a person can erase their sessions too.

An open record

One session record with a published JSON Schema is the contract between the binary and any server. A test fails if the schema in the repository is stale.

Cloud agents

Sessions that run in the cloud are in the ledger too.

A Claude Code session on the web, a Cursor cloud agent or a Codex cloud task runs in a sandbox the platform starts, with a fresh clone of your repository and nothing from your machine. Claude Code and Cursor run the hooks a repository carries; Codex's cloud runs none, but reads AGENTS.md. So one command writes a small script, its hook entries and a section in AGENTS.md, and you commit them.

  • Nothing to set up in the sandbox. The script fetches the sessionly binary once per sandbox and runs it only if it matches the SHA-256 checksum written into the script. On a person's own machine the script does nothing.
  • Filed under whoever started it. In Claude Code's and Cursor's sandboxes git is set up as the agent, so the person is the one the platform names. In Codex's, git is set up as the person who started the task.
  • Shell edits count. In a sandbox an agent often edits with sed or a heredoc instead of its file tools. The working tree is compared before and after each shell command, so those lines are in the session, the rewrite rate and the pull request figures.
  • Sent when a turn ends. A sandbox may be gone minutes later. Where sessions go is set in the cloud environment, not in the repository; without it nothing leaves the sandbox.
  • Tied to its pull request by branch. In Claude Code's and Cursor's clouds the agent commits under its own name, so its session is matched to the pull request of the branch it pushed. A cloud agent's pull request with no captured session is marked as such.

Pull requests

How much of this pull request did an agent write, and how did it fare?

A GitHub Action reports each pull request to your server, which matches the lines it adds against the lines agents added in uploaded sessions. Both sides send hashes: no source code leaves GitHub or anyone's machine.

  • Per pull request: lines added, how many an agent wrote and with which agent and model, review rounds, and comments by people and by review bots. Its own page shows the sessions that wrote it, its files, and a link to each review and comment on GitHub: their text stays there.
  • Who asked for each round: one row for each reviewer, people and each review bot apart, with their reviews, comments on the diff and replies; and how many of its rounds of review followed only bots' feedback, only people's, or both. The Review bots table sums that per bot over the pull requests shown. Version 0.4.0 of the Action says whose feedback each round followed; with an older one that is not known.
  • How often it was reviewed before that: each review command run in the sessions that wrote it, in order: run 2 of 5, how long after the one before, its effort, cost and findings. Beside the review bots' comments on GitHub.
  • What it cost: what was spent on it, not what its remaining lines cost. Every session that gave it lines is counted, also when review removes them, and one that worked on several pull requests is split between them. With it, the cost of an agent line that got through review. It reads "at least" when a session has no cost figure, and is marked ~ when it is an estimate.
  • By model: the same, summed, so you can see whose lines get through review as written and whose take several rounds.
  • A floor, not a guess: a line counts as an agent's only when a session by someone who committed to the pull request added that line to that file. A cloud session counts when it ran on the pull request's branch.
  • Quiet by default: figures go to the run's summary and to a page for admins. A comment on the pull request is yours to switch on.

What is uploaded

Full content stays on the machine. The default upload carries no text.

Each developer's machine decides what a server receives. There are two content levels, and sessionly export <session> prints exactly what would be sent, connected or not.

A preview can contain anything that was typed or run, including a secret. Line hashes are what pull request attribution needs; a hash does not give the line back, but a short or common line can be guessed and checked against it.

Create an organisation

Sessionly is early. A release is a binary for Linux or macOS to unpack, or cargo install sessionly; there is no installer yet. A server of your own has no sign-in: whoever can reach its dashboard is its admin, so keep it on a network you trust. The README says what works today.

Get started

On your own machine in a few minutes.

Unpack the binary from a release (Linux or macOS) or install it with cargo install sessionly, then install the hooks and import the sessions your agents still have. Listing, search, summaries and the rewrite rate all work without a server.

  • Careful with your settings. Only Sessionly's own hook entries are added or removed, and the settings file as it was is saved beside it.
  • Codex asks first. Codex runs a new hook only once you approve it: start codex and accept the hooks it shows, or run /hooks.
  • Easy to undo. sessionly uninstall takes the hooks out again.
  • Try it on one project. sessionly install --project DIR writes to that project's settings only.
One machine
# a release's archive for your system, from GitHub
$ tar -xzf sessionly-*.tar.gz
$ mv sessionly ~/.local/bin/   # or anywhere on your PATH
# or, with Rust installed, from crates.io
$ cargo install sessionly
$ sessionly install   # adds the agents' hooks
$ sessionly import    # past sessions of all four agents
$ sessionly list
$ sessionly summary --by tool
$ sessionly show <session>

For a team, one Docker Compose file.

It starts the server, the dashboard and Postgres. Each developer connects their machine once; after that, sessions upload on their own when a turn ends.

  • Put it behind HTTPS. The binary refuses plain http:// for anything but a server on the same machine.
  • No sign-in. The dashboard opens as its admin for whoever can reach it: keep it on your own network. Each machine connects with a token from the Connect page.
  • Nothing of yours phones home. A self-hosted install sends none of your data to Sessionly. Its dashboard counts which of its pages are opened, by name and nothing else; SESSIONLY_TELEMETRY=off stops that.

A team
# on the server
$ docker compose up -d

# on each developer's machine
$ sessionly connect https://sessionly.example.com --token sly_…

$ sessionly settings --content previews

Read the numbers for what they are.

Cost is the agent's own recorded figure where there is one and an estimate from token counts elsewhere, as for Codex, which records none. It is not an invoice. The rewrite rate measures whether lines survived, not whether they were good or why they changed. The agent share of a pull request is a floor. Names and emails come from git config, or for a cloud session from the platform: a label, not a verified identity.

Start with one machine. Add the team when the numbers are useful.

The code, the session record's schema and the limits of every figure are in the repository.
